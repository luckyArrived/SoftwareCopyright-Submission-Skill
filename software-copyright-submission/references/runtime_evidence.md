# 操作说明的运行证据

核对申报软件、参考源码和实际运行端。已发布网页、开发环境和既有测试记录均可作为证据，明确版本和来源。处理异步功能时，在业务理解中单独声明准备、提交和完成状态，按申报功能核对预览、导出、下载等结果。

在业务理解中将软件界面形态填写为 `interface_type`，使用 `graphical`、`command_line` 或 `headless`。在每个 `manual_modules` 条目中列出 `source_files` 和 `required_evidence_states`，分别对应已选源码路径和必须核验的状态名。将每张图按 `screenshots` 中的标题安排在相应说明旁，例如 `【截图预留：生成完成】`。真实图保存到资料目录内。

完成后写入 `草稿/运行证据.json`，示例如下。给每个手册模块及每个所需状态填写已核对的证据。每张图只插入对应的位置。

```json
{
  "software_name": "示例软件",
  "version": "V1.0",
  "interface": "graphical",
  "features": [
    {
      "module": "清单生成",
      "states": [
        {
          "state": "完成",
          "observed": "结果列表显示两项输入，状态为已生成",
          "origin": "V1.0 本地运行，演示账号，测试任务 T01",
          "slot": "生成完成",
          "image": "截图/02-生成完成.png"
        }
      ]
    }
  ]
}
```

图形界面的每个所需状态都要有图。应在方案中区分不同页面、素材类型、错误提示和成品状态。脚本核对状态和模块对应、图片可读取、插入位置与实际嵌入，图是否真实清晰以及步骤是否全面由核验者打开运行环境和成稿确认。

命令行软件填写真实命令和输出，可按需嵌入终端截图，并说明是否存在独立图形界面。纯服务端、接口或批处理在没有用户运行界面时填写实际调用方式、输入、可核验的响应或落盘结果。此时可省略该状态的 `slot` 和 `image`，同时在顶层增加 `type_in_name` 和 `interface_statement`。前者填入已确认的全称中体现真实类型的文字，例如“命令行”或“服务端”。后者写明运行形态、调用方式与响应。正式 Word 说明以申请表同一全称和版本生成。

手册草稿、证据清单和使用的图片随最终草稿指纹一起核对。需要登录、缺少部署代码、无法复现实际结果时，按状态列出缺项并留在草稿核对阶段。
